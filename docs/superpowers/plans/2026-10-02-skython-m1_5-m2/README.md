# Skython v1 (M1.5 test ESP and probes + M2 events and lifecycle + generic acceptance): plan index

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **How to use this plan:** it is split into one file per task. To do a task, read **this file** (overview, Global Constraints, Contracts, File Structure, the task's brief under its part) and **that task's file** only. Each task file has an **Interfaces** block naming what it consumes and produces; the Contracts section below is the single list of cross-task names, so earlier task files are not required reading. The design spec and `spikes/RESULTS.md` are background, not required reading for a single task.

**Goal:** Finish Skython v1: events and lifecycle (per-subscription bounded queues, subscriptions with filters, the Python event dispatch thread, bridge event frames, the v1 event list, mod events and the native `Skython.Send`, `game.load`/`game.save`), a test plugin `SkythonTest.esp` with the deferred live tests and the three engine probes, and a generic acceptance scenario run through the bridge and in-process.

**Architecture:** A new pure C++ `spy::EventHub` in `core/` owns event consumers, per-subscription bounded queues (drop-oldest with a `dropped` count), per-subscription `seq`, the epoch stamp and equality-set filters; game sinks in the plugin only check `Wants`, build JSON with form references, and `Push` (no Python, no GIL, never blocking). The `Dispatcher` answers `events.subscribe`/`events.unsubscribe` itself through the hub, using a consumer id passed beside the request text (never inside it); `_skython.next_events(consumer, timeout)` drains a consumer with the GIL released. In Python one `skython.events` dispatch thread per `Game` runs callbacks in order for both transports: in-process it drains its own consumer, remotely `RemoteTransport`'s reader thread feeds it from event frames that the bridge's per-connection pump writes, through a client-side bounded queue per subscription (the subscription's `max_queue`, drop-oldest, `dropped` reported on the next delivered event: the same semantics as in-process). `game.load`/`game.save` run in `AddUITask` (spike S6). The test ESP is built on Linux by a Mutagen program kept in its own GPL-3.0-only folder (`testesp/builder/`); its Papyrus sources are compiled on Linux by `tools/papyrus_compile.sh` (spike S5's headless Wine recipe, with the flags file `TESV_Papyrus_Flags.flg`).

**Tech Stack:** as v1 (C++20 core and pyglue on g++ 11 / MSVC v143, C++23 plugin, CommonLibSSE-NG pinned submodule, nlohmann/json 3.11.3, doctest 2.4.11, pybind11 3.1.0, spdlog, CPython 3.14.8 in the game, Python ≥3.12 for `skython`, pytest, uv) plus: Papyrus Compiler (the SimpleSkyrim copy, run headless under GE-Proton10-14's `wine64`), .NET SDK 8.0.424 at `~/.dotnet/dotnet`, `Mutagen.Bethesda.Skyrim` 23.4.0 (already in `~/.nuget/packages`), Python `tomllib` (stdlib).

**Spec:** `docs/specs/2026-09-30-skyrim-python-design.md` (draft 4). Sections 4.3, 4.5, 4.6, 4.7, 5, 8 and 9 matter most to whoever coordinates the plan.

**Scope of this plan:** M1.5 (test ESP, the three spec probes, the property and alias live tests deferred from v1 Tasks 29-30), M2 (events, lifecycle, `game.load`/`game.save`, live event tests, soak) and a **generic acceptance scenario**. Skython is a general-purpose bridge: no task designs an API, event, name or test around one consumer, and user-facing docs (`README.md`, `examples/`, `docs/` other than specs and plans) never mention skyrim-dm. The acceptance scenario's quest function name `SetupScenario` and channel `skython_test` are the proposal in **owner decision 8** (`OWNER-DECISIONS-2026-10-02.md`); they are used only if the owner accepts decision 8 (see Gates). ## Global Constraints

Carried over verbatim from the v1 plan (every one still applies):

- CPython **3.14.8**, standard GIL build, x64. Runtime: the unmodified `python-3.14.8-embed-amd64.zip`. Build inputs: `tools/include/` and `tools/libs/python314.lib` from the NuGet package `python` 3.14.8. Both fetched by `tools/fetch_python.sh` and checked against SHA-256 values recorded in `docs/PINS.md`. Never a free-threaded build.
- pybind11 **3.1.0**, vendored under `third_party/pybind11/` (headers only).
- **SKSE tasks, the game's own threads and the Papyrus VM's threads never execute Python and never take the GIL.** Event sinks and VM callbacks produce C++ values and JSON text only.
- **"Main thread" in the Part C task files means "inside an SKSE task"** (ruling R49, measured in spike S7, Task 9): `AddTask`/`AddUITask` tasks are serialized (observed: 0 overlapping in about 2800 probed tasks, not proven) and run on varying BSJobs job threads; the window thread (`RE::Main::threadID`, the plugin-load thread) runs none. Never identify "the main thread" by thread id. (In this plan the rule covers every task that runs in the game: Parts E, F and G.)
- **Two DLLs** (spec 4.1). `python314.dll` exports data symbols, so it cannot be delay-loaded (MSVC LNK1194). The loader `Data/SKSE/Plugins/Skython.dll` has no Python headers or imports; in `SKSEPlugin_Load` it checks the runtime, checks `GetModuleHandleW(L"python314.dll")` (a module of that name from another path → Python disabled, the log names that path), then `LoadLibraryExW(<plugin dir>\Skython\python\python314.dll, nullptr, LOAD_WITH_ALTERED_SEARCH_PATH)`, then `LoadLibraryExW(<plugin dir>\Skython\SkythonCore.dll, nullptr, LOAD_WITH_ALTERED_SEARCH_PATH)`, then calls the core's export `extern "C" __declspec(dllexport) bool SpyCore_Load(const SKSE::LoadInterface*)`. Every failure is logged and the loader still returns `true` (the game runs without Python). The core links `python314.lib` normally and holds everything that touches Python, pybind11 or the game.
- CPython is initialised once, on the host thread, with `Py_InitializeFromConfig` and an isolated `PyConfig` (`isolated = 1`, `use_environment = 0`, `install_signal_handlers = 0`, `site_import = 1`, explicit `home`, `module_search_paths_set = 1`; the zip's `python314._pth` is then ignored). **Never `Py_Finalize`.** After `skython._host.main()` returns, the host thread calls `PyEval_SaveThread()` and blocks forever on a condition variable; it never ends while holding the GIL. That mutex and condition variable are deliberately leaked (`new`, never deleted, never static objects): a static one is destroyed at process exit while the host thread still waits on it, which hung exit in the Linux test of spike S8.
- No work in `DllMain`; the host thread starts at `kDataLoaded`; game calls run only after `kDataLoaded` and the interactive signal.
- The boundary between Python and C++ is request/response JSON text plus a few scalars (`_skython` Contract below). No `PyObject` is converted in C++ beyond `str`, `int`, `float`, `None`.
- **Papyrus dispatch rules from spike S2 (box, 2026-10-01):** (1) never call `Dispatch*Call` with a class or function that was not first found with `FindFunction` and argument-checked: an unresolvable target crashes the engine (`SkyrimSE.exe+1447D3E`, null deref); (2) the VM never frees `IFunctionArguments`: the plugin owns them, frees them in the VM callback after reading the result, never earlier (measured: phase D, 1000/1000); when `Dispatch*Call` returns false the plugin does NOT free them (unmeasured: the callback might still fire, so freeing could double-free) but logs it once as a leak — with rule (1) a false return is not expected at all; (3) the callback may run inside an SKSE task or on a VM thread: never assume either, and never test the thread id to tell (R49).
- One `AddTask` per request or batch step, plus at most one more to convert an object result (a form, an alias or an array of objects): none when the VM callback runs synchronously inside our own task (a `thread_local` flag our tasks set, R52; never a thread-id test, R49), one otherwise; the work runs in an SKSE task: serialized (observed), on varying job threads; the window thread runs none (R49). A task never re-queues itself.
- Dev bridge: TCP bound to `127.0.0.1` only, default port `45977`, non-loopback peers refused, 128-bit random token as 32 lowercase hex characters, framing 4-byte little-endian length + UTF-8 JSON, max frame 16 MiB, protocol `[1, 0]` (major mismatch refused). `bridge_enabled = false` in the shipped ini, `true` in the dev ini. (This plan raises the minor to `[1, 1]` in Task 33; the major stays 1 and the rule stands.)
- Papyrus Int is 32-bit signed: out of range is `type_mismatch`, never truncation. Papyrus arrays hold at most 128 elements.
- No raw engine pointers kept across tasks; every task re-resolves by FormID.
- No exception may escape a thread the plugin owns: every main-thread task, VM callback, sink, the reaper thread and the host thread catch `std::exception` and `...`; a failure becomes an `internal` error or disables Python, never a game crash. Every Python entry point called by the plugin or `skython._host` is wrapped in Python and logs the traceback.
- JSON text that leaves C++ is produced only by core's `spy::dump_json` (invalid UTF-8 replaced, never thrown). Request text from Python is checked with `spy::nesting_within` (depth 64) before it is parsed.
- CommonLibSSE-NG: `alandtse/CommonLibSSE-NG`, branch `ng`, pinned submodule at `39f9d07a6ffabea8fb559eee87ab7d27cd463e8a` (v10.1.0). Use the signatures in `API-VERIFICATION.md`, not memory. Never use skyrim-re-toolkit's vendored copy. Known MSVC pitfalls from the build box: define `NOMINMAX` and `WIN32_LEAN_AND_MEAN`; `#undef GetObject` after the includes in every TU that calls `Variable::GetObject()`; never call `TypeInfo::GetTypeInfo()` (or `TypeAsString()`) on an object-array type: at the pin it masks with `~0xB` and returns a class pointer 8 bytes off (crashed the game in S7); use `raw & ~1` for an object array's class; `REL::Module::get().version().string(".")`; `SKSE::Init(skse, { .log = false })`.
- Verified runtime: AE 1.6.1170, Windows-native on the build box (ruling R51; Proton deferred until the owner says the Linux machine is free). The plugin refuses to start Python on an unsupported runtime (log the version and why). Release notes list only verified runtimes.
- `skython` package: Python ≥3.12, standard library only at runtime; tested on 3.12 and 3.14. Sync API only in v1.
- Licence: MIT. Copy no code from Chronicle (AGPL), SkyrimPlatform or DevBench (GPL). IntelEngine (Apache-2.0) and SkyLink (no LICENSE file) are read-only references. Bundle the CPython licence (`LICENSE.txt` from the embeddable zip) with any deployed runtime.
- Commits: conventional style, no AI attribution lines (global rule; overrides harness trailers). Never `git push` without the owner saying so.
- Never delete files with `rm`; use `gio trash` only after the owner approves an itemised list (global rule). Applies to the Windows box too (no `Remove-Item`).
- The Windows build box's default SSH shell is Windows PowerShell 5.1 (not cmd.exe); every remote command is PowerShell syntax, every ssh/scp call has a timeout and `BatchMode`, every wait loop is bounded and prints the log tail on timeout.
- The RTX 5080 is reserved for TTS: no step may use or reconfigure the GPU.
- The game runs on the Windows box (Task 1b): no step launches the game on the Linux desktop, uses xdotool, or starts Linux Steam, unless the owner says the Linux machine is free. On the box, our files go only under `Data\SKSE\Plugins` (DLLs, `Skython\`), the one file `Data\Scripts\SkyrimPython.pex`, and `C:\dev\skyrim-python-box`; never modify ChronicleDev's existing files, tasks or saves.

## Review Focus

1. **An event flood** (a melee fight raising `hit` many times per frame, dozens of `cell_attach` at a load) → `Push` never stalls the game: each subscription's queue stays at its `max_queue` (drop-oldest), the next delivered event carries `dropped`, memory stays bounded, and frame time does not move. Remotely the same holds on the client: the bridge's pump drains the hub continuously, so the bound is the `RemoteEventStream`'s per-subscription queue (the subscription's `max_queue`, drop-oldest, client-side drops added to `dropped`), and the bridge's `max_queued_bytes_per_connection` bounds the server side. Hub memory is bounded twice per consumer: at most `max_subscriptions_per_consumer` (256) subscriptions, and at most `max_queued_event_bytes_per_consumer` (16 MiB) of queued events (data length plus a 96-byte envelope each), beyond which the oldest frames of the pushed subscription are dropped and counted in `dropped` (ruling R61). Pinned in Task 34 (unit: 10^6 pushes into a 16-slot queue with no consumer, bounded size, exact `dropped`; the byte budget lowered through `EventHubOptions::max_queued_bytes_per_consumer` drops oldest with exact `dropped`; the 257th subscription of one consumer is `busy`), Task 37 (remote: 10^4 pushes to a `max_queue` 16 subscription whose callback blocks; the client queue never exceeds 16 and `dropped` sums exactly), Task 40 (live: a filtered `hit` subscription during scripted combat with the drain meter) and Task 56 (soak).
2. **A slow Python callback** (one that sleeps 2 s per event) → its queue fills, drops are counted and reported on the next delivered event, other subscriptions of the same `Game` are still delivered in order once it returns, other `Game`s and bridge connections are unaffected, and the game never waits. The same holds for a remote `Game` (client-side bounded queue, Contracts: `RemoteEventStream`). Pinned in Task 34 (unit), Task 35 (`_skython` with fake pushes while no one drains), Task 36 (slow callback test, in-process), Task 37 (slow remote callback: `dropped` reported, a second remote subscription keeps its order, and a second bridge connection's `Game` keeps receiving events while the first connection's callback is blocked) and Task 53 (live overflow with a sleeping callback, in-process and through the bridge).
3. **Events raised during a save load** (from `kPreLoadGame` or `kNewGame` until the `game_loaded` push: `life::SaveLoadInProgress()`, ruling R60) → events whose table entry says `deliver_while_loading: false` are not queued and are counted in `suppressed` on that subscription's next delivered event; `menu_open`, `menu_close`, `mod_event`, `channel` and the lifecycle events are delivered; `game_loaded` marks the end of the load. **Ordinary loading screens (doors, fast travel, `coc`) suppress nothing**: `player_location` and `cell_attach`/`cell_detach` raised by such a transition are delivered. Pinned in Task 34 (unit with a fake `loading` source), Task 35 (fake), Task 40 (live: a door or `coc` transition delivers `cell_attach`/`cell_detach` and a location change delivers `player_location`, checked with `Actor.GetCurrentLocation` before and after) and Task 42 (live: subscribe to `cell_attach` and load a save: `suppressed`).
4. **Unsubscribe and close races** (closing a `Subscription` or the `Game` while its callback runs on the dispatch thread, a bridge client disconnecting with events queued) → once `close()` returns no callback of that subscription starts; `close()` called from inside a callback does not deadlock; a disconnect closes that connection's consumer and every subscription it owned. Pinned in Task 36 (Python: close during a running callback, close from inside a callback, `Game.close` with 8 subscriptions) and Task 37 (bridge: disconnect with 1000 queued events, consumer count back to its baseline).
5. **Save and load with live subscriptions** → subscriptions survive the load, event frames after it carry the incremented `epoch`, and a form reference from an event of the old epoch either still works (plugin-defined forms, runtime forms whose fingerprint matches) or raises `StaleReference`/`NotFound` on use, never a crash. Pinned in Task 42 (live, vanilla forms and a `PlaceAtMe` item) and Task 53 (live, the ESP's persistent NPC and its death event after a reload).
6. **A sink describing a form while it is being loaded or unloaded** (a `cell_attach`/`cell_detach` burst at a load or a cell unload) → no crash: `pv::DescribeFormForEvent` touches only data valid on the sink's thread (form id, file, form type, the prebuilt class table; never the VM) and a form it cannot describe becomes `null` or a reference without fingerprint. Pinned by Task 42 (a save load with `cell_attach` subscribed) and Task 40 (the `coc` transition test with `cell_attach`/`cell_detach` subscribed).

### Protocol additions (Task 33; `protocol.json`, generated tables, fixtures)

Protocol becomes `[1, 1]` (minor bump: new ops and the events table; a `[1, 0]` client still connects).

New ops (all four are listed in the welcome's `capabilities`):

| op | batchable | needs_game | args | result |
|---|---|---|---|---|
| `events.subscribe` | no | **no** | `event` (`event_name`, required), `filter` (`event_filter`, optional), `max_queue` (`queue_size`, optional, default `default_event_queue`) | `{"sub": <uint64>, "event": "<name>", "max_queue": <n>}` |
| `events.unsubscribe` | no | **no** | `sub` (`u64`, required) | `null` |
| `game.save` | no | yes | `name` (`save_name`, required), `timeout_ms` (optional) | `{"name": "<name>"}` once the game's `kSaveGame` message for that name arrives: **the engine started the save**; the `.ess` file can appear a moment later |
| `game.load` | no | **no** | `save` (`save_name`, required), `timeout_ms` (optional) | `{"save": "<name>", "started": true}` once the UI task's load call returned true |

- The consumer that owns a subscription is **never in the request**: it travels beside the request text (`_skython.submit(text, consumer)`, below). The bridge forwards request text unchanged, as PROTOCOL.md already says, so a client cannot name another consumer. An `events.*` request submitted without a consumer (consumer 0), or with an unknown or closed consumer, is refused, in core and in the Python fake alike: consumer 0 → `bad_request` `no event consumer` (exactly, answered by the Dispatcher); `events.subscribe` on an unknown or closed consumer → `bad_request` `no event consumer <n> (never opened, or closed)`; `events.unsubscribe` on an unknown or closed consumer → `not_found` `no subscription <sub> for this consumer` (the same answer as another consumer's sub).
- New arg types: `event_name` (one of the events table's names, else `bad_request` naming the event), `event_filter` (object, rules below; `"filter": null` or an absent `filter` means no filter), `queue_size` (integer 1..`max_event_queue`), `u64` (non-negative integer ≤ 2^64-1), `save_name` (string matching `^[A-Za-z0-9_]{1,64}$`, else `bad_request`).
- New limits: `default_event_queue` = 1024 (spec 4.6), `max_event_queue` = 65536, `max_subscriptions` = 1024 (all consumers together; beyond it `busy`), `max_subscriptions_per_consumer` = 256 (one consumer's 257th subscription is `busy` with the message `consumer <n> has 256 subscriptions (max_subscriptions_per_consumer)`, so one bridge client cannot starve in-process scripts; R61), `max_queued_event_bytes_per_consumer` = 16777216 (16 MiB of queued frame text per consumer; over it the oldest frames of the pushed subscription are dropped, counted in `dropped`, rule under the C++ core below; R61), `max_filter_values` = 128 (per filter field), `max_events_per_next` = 256, `max_channel_payload_bytes` = 65536 (a longer `Skython.Send` payload is cut at a UTF-8 boundary and the event carries `truncated: true`), `max_channel_bytes` = 256 (a `Skython.Send` whose channel is empty or longer than this is **dropped** and a warning is logged once; a channel is never truncated, because a cut name would be a different channel). `protocol.json` also gains a top-level `save_name_pattern` (`^[A-Za-z0-9_]{1,64}$`), generated as `spy::kSaveNamePattern` and Python `SAVE_NAME_PATTERN`.
- New config keys: `trace_timing` (bool, default false; dev only: GameBackend logs per-request timestamps, Task 38), `console_echo_errors` (bool, default true: script failures echo one rate-limited line to the in-game console, Task 43). `enable_console` keeps its v1 meaning (the native console op, off). Task 33 also adds them to the hand-written config code: `Config::trace_timing` (bool, false) and `Config::console_echo_errors` (bool, true) in `core/include/spy/config.h`, parsed by `parse_config`, emitted by `config_to_json` (so `_skython.config()` and `settings::Get()` carry them), generated `config_defaults::kTraceTiming` and `config_defaults::kConsoleEchoErrors`, unit tests in `test_config.cpp`. The rule "`needs_game` is false only for `game.state`" is not a header comment but is pinned in tests (`core/tests/test_generated.cpp`, `tools/test_gen_protocol.py`, `python/tests/test_generated.py`); Task 33 rewrites those tests to the new set `game.state`, `events.subscribe`, `events.unsubscribe`, `game.load`.
- `events.unsubscribe` of an unknown sub, or one owned by another consumer → `not_found`. Subscribing to an event whose table entry has `filter_required_any_of` without at least one of those fields → `bad_request` ("hit needs a filter on target or aggressor").
- `game.save`: an existing save with that name → `bad_request` with the message `a save named <name> already exists` and `detail.reason = "save_exists"` (never overwrites); in the plugin, a second `game.save` of a name whose save is still pending, or **announced** (its `kSaveGame` arrived but its `.ess` is not on disk yet; names compared case-insensitively) → `bad_request` `a save named <name> is already in progress` with the same reason (Task 41). No `kSaveGame` within the timeout → `timeout`. The result (and the `game_saved` event) means the engine **started** the save, not that the file is written. `game.load` of an announced save whose `.ess` is not on disk yet → `not_ready` with the message `save <name> is still being written` and `detail.reason = "saving"` (a new entry in `protocol.json`'s `not_ready_reasons`, Task 33; plugin only, the fakes never produce it); a client retries briefly. While a `game.save` is pending, `game.load` is `busy` `a game.save is in progress; load after it completes`; while another `game.load` is queued, `busy` `another game.load is already queued`. When the plugin cannot find the save folder (no SKSE log folder at `kDataLoaded`), both ops answer `internal` `save folder unknown (...)`. These plugin-only answers are not fixtures. `game.load`: no such save → `not_found` with the message `no save named <name>`; these two texts are fixed by `responses.json` ids 64 and 65 (Task 33) and are what `FakeBackend` (Task 35), the Python fake (Task 36a) and the plugin (Task 41) produce; refused while `NotReadyReason` is `"starting"` or `"loading"` (`not_ready`); the engine's load call returning false → `internal` naming the save. `game.load` is `needs_game: false` on purpose: the load it starts is a world reset that cancels every in-flight `needs_game` request, so a `needs_game` load would cancel itself; and loading from the main menu works (S6). Because the Dispatcher therefore skips its readiness check for `game.load`, `saveload::Run` (and `FakeBackend`) check `NotReadyReason(false)` themselves and answer `not_ready` for `"starting"` and `"loading"` (a `"no_game"` main menu is allowed).

**Event frame** (extends the line already in PROTOCOL.md; `dropped` and `suppressed` are new and present only when non-zero):
```json
{"type":"event","event":"death","sub":7,"seq":12,"epoch":3,"data":{"victim":{"kind":"form",...},"killer":null},"dropped":4,"suppressed":2}
```
- `seq`: per subscription, starts at 1, +1 for every event accepted for that subscription (whether later delivered or dropped), so gaps equal drops. `epoch`: `LifecycleState::epoch()` when the event was pushed. `dropped`: events of this subscription discarded by overflow since its previous delivered event (drop-oldest). `suppressed`: events of this subscription not queued because a load was in progress (rule below) since its previous delivered event.
- `next_events` returns event objects in exactly this shape (with `"type":"event"`), so the bridge writes each one as one frame with the same fields (Task 37's pump re-encodes the decoded object; field values are unchanged).

**Filters** (`event_filter`): a JSON object mapping a field name from the event's `filter_fields` to a non-empty array of at most `max_filter_values` values. An event matches when every listed field's value is in its array (AND across fields, OR within one). Form fields: each item is a form reference that carries `form_id` (a form key alone is `bad_request`: "resolve the form first"; Python helpers pass `Form` objects that always carry it); matched by form id; a `null` event field never matches. Int fields: integers. String fields: strings, matched ASCII-case-insensitively (the engine's string pool can change case, ruling R56 / Task 28). An unknown field or an empty array is `bad_request`.

**Loading rule:** while the hub's `loading` source is true, an event whose table entry has `deliver_while_loading: false` is not queued; each matching subscription's `suppressed` count goes up by one. In the plugin that source is `life::SaveLoadInProgress()` (ruling R60): true from `kPreLoadGame` or `kNewGame` until the `game_loaded` push (also cleared by a failed `kPostLoadGame`); **never** for door, fast-travel or `coc` loading screens, whose `player_location` and `cell_attach`/`cell_detach` events are delivered. The interactive signal after a load or new game raises `game_loaded`, the boundary consumers wait for. An event sampled as "not loading" just before a load starts can be queued after `game_loaded` with the old epoch: consumers compare `epoch`, never the order relative to `game_loaded` (PROTOCOL.md "Loading", Task 33).

### C++ core (`namespace spy`, `core/include/spy/events.h`, Task 34)
```cpp
using SubId = std::uint64_t;       // from a counter, never reused, starts at 1
using ConsumerId = std::uint64_t;  // from a counter, never reused, starts at 1; 0 means "none"
inline constexpr std::size_t kEventFrameOverheadBytes = 96;  // added to each queued event's data length (byte budget)
struct EventFilter { std::vector<std::pair<std::string, std::vector<json>>> any_of; };  // validated; empty = match all
EventFilter parse_event_filter(std::string_view event, const json& filter);  // throws ProtocolError(bad_request)
bool filter_matches(const EventFilter&, std::string_view event, const json& data);
struct EventHubOptions {
    std::function<std::uint32_t()> epoch;   // life::Epoch in the plugin; a counter in tests
    std::function<bool()> loading;          // life::SaveLoadInProgress in the plugin (R60); a switch in tests
    std::size_t max_queued_bytes_per_consumer = kMaxQueuedEventBytesPerConsumer;  // R61; tests lower it
    // Task 44 adds, only if its probe PASSes, one optional last member (initializers that set it use designated
    // initializers: .epoch = ..., .loading = ..., .on_wanted = ...):
    // std::function<void(std::string_view event, bool wanted)> on_wanted;  // called outside the hub's lock when an
    //                                                                      // event's subscriber count goes 0->1 or 1->0
};
class EventHub {
 public:
    explicit EventHub(EventHubOptions);
    EventHub(const EventHub&) = delete;
    EventHub& operator=(const EventHub&) = delete;
    ConsumerId OpenConsumer();
    void CloseConsumer(ConsumerId);                  // drops its subscriptions and queued events; wakes a waiting Next; idempotent
    json Subscribe(ConsumerId, const json& args);    // {sub, event, max_queue}; throws ProtocolError (bad_request, busy)
    void Unsubscribe(ConsumerId, SubId);             // purges that subscription's queue; throws ProtocolError(not_found)
    bool Wants(std::string_view event) const;        // lock-free (per-event atomic subscriber count)
    void Push(std::string_view event, json data);    // filters, stamps epoch/seq, drop-oldest; never throws, never waits
    std::vector<std::string> Next(ConsumerId, std::chrono::milliseconds max_wait,
                                  std::size_t max_events = kMaxEventsPerNext);  // frame texts in push order across
                                                     // the consumer's subscriptions; empty on timeout or unknown consumer
    std::size_t Consumers() const;
    std::size_t Subscriptions() const;
    std::uint64_t DroppedTotal() const;
    std::uint64_t SuppressedTotal() const;
};
```
Rules: one mutex for queues plus one condition variable per consumer (held by `shared_ptr`, notified after unlocking); `Next` merges the consumer's subscriptions in push order with a min-heap; `Push` evaluates `loading()` once per call, outside the hub's lock; after `Unsubscribe` or `CloseConsumer` returns, `Next` never returns an event of that subscription; all JSON text is made with `dump_json`. An empty `epoch` stamps 0 and an empty `loading` means "never loading"; `Subscribe` on consumer 0, an unknown or a closed consumer is `bad_request` (message starting `no event consumer`); `Unsubscribe` of an unknown sub, of another consumer's sub, and on an unknown or closed consumer are all `not_found` with the same message (`no subscription <sub> for this consumer`); `Next` on an unknown or closed consumer returns empty at once, and with `max_events == 0` returns empty; frame texts are `{"type":"event","event","sub","seq","epoch","data"}` plus `dropped`/`suppressed` when non-zero. **Per-consumer bounds (R61):** a consumer's 257th subscription (`kMaxSubscriptionsPerConsumer`) is `busy` (message `consumer <n> has 256 subscriptions (max_subscriptions_per_consumer)`), checked besides the global `kMaxSubscriptions`; the hub counts each queued event as `dump_json(data).size() + kEventFrameOverheadBytes` (96, for the frame envelope, whose `sub`/`seq` differ per subscription; measured once per push outside the lock) per consumer, and after queuing an event, while the consumer's queued bytes exceed `max_queued_bytes_per_consumer`, it drops the oldest event of the pushed subscription (counted in that subscription's `dropped`); if that subscription has nothing older and the consumer is still over budget, the new event itself is dropped (its `seq` was assigned, so the gap still equals `dropped`).
