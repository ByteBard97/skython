Technical Feasibility Report: Python Embedding and Papyrus Bindings in Skyrim SE/AEThe integration of a Python runtime within a CommonLibSSE-NG plugin to interface with Skyrim's Papyrus Virtual Machine is technically feasible, though it requires meticulous architectural planning regarding thread synchronization, memory isolation, and engine-safe execution. The foundational C++ ecosystem provides robust mechanisms for bypassing raw memory manipulation by utilizing the engine's native virtual machine dispatchers. However, a significant engineering effort will be required to develop a bespoke Papyrus-to-Python stub generator, as no off-the-shelf solution currently exists for this exact translation pathway. The most critical architectural decision hinges on mitigating the inherent conflicts between the synchronous Python Global Interpreter Lock (GIL) and the heavily asynchronous, queue-driven nature of Skyrim's main game thread.Architectural Hosting Paradigms and Interpreter InitializationEmbedding a language runtime directly into a dynamically linked library (DLL) loaded by a host executable presents immediate initialization hazards, particularly concerning Windows loader lock. Initializing a complex runtime like CPython within DllMain is a documented anti-pattern that leads to application deadlocks. In the context of SKSE, initialization must be deferred until the engine broadcasts a safe initialization state, specifically the kDataLoaded message.When CPython initializes, it defaults to registering its own OS-level signal handlers. If executed blindly within an SKSE plugin, this behavior overrides the game engine's native crash and signal handling routines, complicating debugging and potentially destabilizing the host process. The C-API provides explicit bypasses for this behavior; historically through Py_InitializeEx(0), and in modern iterations via the PEP 587 initialization configuration by setting install_signal_handlers=0.Furthermore, the introduction of a Python DLL into the SKSE ecosystem raises the risk of runtime collisions if multiple independent mods attempt to host Python. Sharing a single global interpreter state across independent, unaware plugins is highly susceptible to namespace pollution, module version conflicts, and unexpected state mutation. To guarantee isolation, the architecture must leverage CPython's sub-interpreter functionality via Py_NewInterpreter(). Sub-interpreters maintain entirely distinct environments within the same physical process. Coupled with isolated configuration flags, such as Py_IsolatedFlag (or PyConfig.isolated), the embedded environment can be sandboxed from the user's global site-packages, ensuring deterministic execution regardless of the host machine's external Python configuration.The choice between embedding the interpreter directly within the SKSE plugin (in-process) versus launching a hidden child process communicating via local sockets (out-of-process) represents a classic tradeoff between latency and fault isolation. An in-process implementation benefits from near-zero latency, sharing a direct memory space with the game engine. However, any unhandled segmentation fault within the Python script or a failure to properly release the GIL will result in an immediate unrecoverable crash to desktop (CTD). Conversely, an out-of-process architecture isolates guest execution. A scripting crash in a child process simply severs the IPC socket, allowing the C++ host plugin to gracefully handle the failure and even hot-reload the interpreter without requiring a game restart.Interface Generation and Header ParsingTo provide modders with a native-feeling, strongly-typed Python API, the architecture requires type stubs (.pyi files) reflecting the Papyrus game state. While the Skyrim modding ecosystem contains sophisticated parsers, they are optimized for entirely different outputs. The Caprica project provides a highly optimized C++ compiler for transforming .psc files into binary .pex files. Conversely, Champollion serves as a decompiler to reverse .pex binaries back into readable .psc syntax. Build automation tools like Pyro manage the compilation pipeline but do not parse abstract syntax trees (AST) for language translation.The closest functional precedent is Papyrus-2-Typescript, a specialized utility designed for the SkyrimPlatform project that parses .psc headers and generates equivalent .ts files. Because no equivalent .psc to Python stub generator exists, the project must either adapt an existing open-source AST parser (like Caprica) or engineer a custom parser. This parser must consume distributed headers from vanilla Skyrim, SKSE, and community libraries (like PO3) and output compliant Python interfaces.Virtual Machine Dispatch and Engine InterfacingDirect manipulation of engine memory via reverse-engineered offsets is highly brittle, often breaking across minor game updates. CommonLibSSE-NG mitigates this by wrapping the engine's internal virtual machine interfaces. Through RE::BSScript::Internal::VirtualMachine, developers can invoke Papyrus functions by string name, leveraging the engine's native parameter validation and execution queue.The dispatcher utilizes DispatchStaticCall() for global functions and DispatchMethodCall() for object-bound member functions. This design provides a profound stability advantage: so long as the Papyrus script signature remains unchanged, the C++ invocation will survive engine binary updates. However, this safety introduces latency. Translating native C++ types into Papyrus BSScript::Variable types, pushing them through the VM queue, and waiting for execution incurs a measurable overhead compared to raw memory writes. High-frequency polling utilizing these dispatchers is not recommended due to the risk of VM stack overload.Thread Synchronization and Memory SafetySkyrim's architecture is fundamentally intolerant of off-thread memory access. Operations modifying game state must be executed on the main game thread. When an embedded Python interpreter executes asynchronously, it cannot directly invoke engine APIs. Doing so invites immediate race conditions and memory access violations.The accepted pattern involves the SKSE task interface, which allows external threads to push functor objects onto a queue that the main thread consumes safely during its execution loop. The integration layer must provide Python with asynchronous constructs (e.g., Python asyncio Futures) that wrap these queued SKSE tasks.Furthermore, game objects cannot be safely represented in Python as raw C++ pointers (e.g., TESObjectREFR*). The engine's garbage collector and cell-loading routines routinely invalidate memory addresses. To ensure memory safety, all Python representations of game objects must store the immutable 32-bit Form ID or the engine's BSHandleRef. When a Python script queues a read/write task, the C++ layer must safely resolve the handle on the main thread before execution; if the object has been unloaded or destroyed, the task resolves with a failure state rather than causing a segmentation fault.High-Performance Event SinkingBecause routing high-frequency events through the Papyrus VM incurs severe performance penalties, a native event layer is required for optimal performance. CommonLibSSE-NG exposes the engine's internal event dispatchers through the BSTEventSink template interface.By creating custom C++ sinks for critical high-frequency engine events—such as TESHitEvent (combat impacts), TESDeathEvent (actor mortality), and TESEquipEvent (inventory modifications)—the plugin can intercept game state changes instantaneously. These lightweight sinks serialize the event data into thread-safe queues, which the Python interpreter can consume at its own pace. This hybrid approach leverages C++ for high-performance event interception while delegating the complex, stateful business logic to Python.Structured Feasibility AnalysisThe table below outlines the core technical requirements, supported by available documentation and community precedent, along with the subsequent architectural impact on the mod's development.Sub-QuestionAnswer SummaryEvidence (URL, Label, Date, Quote)ConfidenceArchitectural Impact1.
