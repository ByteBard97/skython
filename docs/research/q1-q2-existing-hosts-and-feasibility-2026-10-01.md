# Python-in-Skyrim mod — Research: Questions 1 & 2

Date of research: 2026-10-01. Evidence labels: **V** = page opened and read; **U** = search result/snippet only; **R** = recall. Nexus Mods pages returned errors to automated fetches in several cases; those are marked as dead ends, not verified.

# Question 1. Does a Python (or generic) scripting host for Skyrim already exist?

**Verdict: Build — do not adopt, adapt only in fragments.** No existing project delivers what Part A describes: a player-shippable Python interpreter hosted by an SKSE plugin with a native-feeling Papyrus API. The closest thing by architecture is SkyLink AI (generic Papyrus VM bridge over a named pipe, self-described MIT), but it is an MCP/AI-dev bench, not a scripting host, and its GitHub licence metadata is missing. SkyrimPlatform proves the whole concept works in-process (generic JS calls into Papyrus, hot reload, async/latent handling) but is GPL-3.0, JavaScript-only, and openly admits weak savegame support. SkyrimPy is the only true CPython-in-SKSE attempt and it died on the day it was created. JContainers' new Lua runtime shows an embedded interpreter with two-way Papyrus integration is a live, maintained pattern — in Lua, not Python.

### 1.1 SkyrimPlatform / SkyMP

- **What it is:** JavaScript/TypeScript mod host (ChakraCore engine + Chromium Embedded Framework UI), distributed as an SKSE plugin; part of the SkyMP multiplayer project ([github.com/skyrim-multiplayer/skymp](https://github.com/skyrim-multiplayer/skymp), **V**, opened 2026-10-01: "SkyMP is an open-source multiplayer mod for Skyrim … built on top of the SkyrimPlatform"). Type definitions live in a separate repo [skyrim-platform/skyrim-platform](https://github.com/skyrim-platform/skyrim-platform), "GPL-3.0 license" shown on the repo page (**V**). SkyMP's TERMS.md requires disclosing source of forks: "TL;DR disclose the source code of your forks" (**V**, same repo).
- **Supported runtimes:** "Steam latest (currently Skyrim SE/AE 1.6.1170); Skyrim SE/AE 1.6.640; Skyrim SE 1.5.97.0.8 (Deprecated, not accepting bugs anymore)" ([skyrim-platform/README.md](https://github.com/skyrim-multiplayer/skymp/blob/main/skyrim-platform/README.md), **V**, opened 2026-10-01). No mention of 1.7.99/1.7.104 support anywhere on the page — the README still calls 1.6.1170 "currently" latest, so 1.7.x support is **unverified/likely absent**.
- **TypeScript definitions:** hand-maintained, not generated from `.psc`. Versioning note: "SP follows Semantic Versioning for JavaScript, but not for TypeScript… updating `skyrimPlatform.ts` may break the compilation" ([docs_skyrim_platform.md](https://raw.githubusercontent.com/skyrim-multiplayer/skymp/main/docs/docs_skyrim_platform.md), **V**). A third-party converter exists for SKSE library headers: [CarlosLeyvaAyala/Papyrus-2-Typescript](https://github.com/CarlosLeyvaAyala/Papyrus-2-Typescript), "Converts Papyrus \*.psc header files to \*.ts files ready to use in Skyrim Platform" (**V**); MIT licence, last push 2023-02-06 (GitHub API, **V**).
- **Threads/lifetimes/save-load:** features list claims "Promises and async/await support… for async Papyrus functions like `Utility.wait`" and "Safety. SP protects you from null pointers, threadding issues" (**V**, README). But also: "Inadequate savegame support: managing the game state can be tricky" and "Updating/deleting SkyrimPlatform on a current save might break your save" (**V**, README). Hot reload is first-class: "Ctrl+S, Alt+Tab, and you can test your changes in-game" (**V**).
- **External interface:** plugins are JS files in `Data/Platform/Plugins`; it has HTTP and Win32 APIs, so an external process could reach it, but there is no documented socket/pipe RPC for an external interpreter. **U/inference.**
- **Confidence: high** on licence/versioning/scope. **What this changes for us:** proves in-process interpreter + generic Papyrus calls + hot reload works at scale; GPL-3.0 plus CEF weight means we borrow the design, not the code.

### 1.2 SkyLink AI (jarvann/SkryimMCM)

- **What it is:** "A Model Context Protocol (MCP) server that lets AI assistants… interact directly with Skyrim SE/AE's runtime engine. 74 tools for reading and modifying game state in real time" ([github.com/jarvann/SkryimMCM](https://github.com/jarvann/SkryimMCM), **V**, opened 2026-10-01). Architecture: `Claude Desktop <-stdio/MCP-> C# MCP Server <-named pipe-> SKSE Plugin`, pipe `\\.\pipe\SkyrimMCP` (**V**).
- **Generic Papyrus call: yes.** Feature list includes "Papyrus — Function catalog (3,389 functions from 166 scripts), script function lookup, VM call bridge" and source files `PapyrusBridge.*` ("Papyrus VM bridge"), `EventSystem.*` ("Game event sinks"), `TaskQueue.*` ("Game thread dispatch") (**V**, README project structure).
- **Licence: ambiguous.** README says "## License — MIT" (**V**), but the GitHub API reports `"license": null` — no LICENSE file detected (api.github.com/repos/jarvann/SkryimMCM, **V**, 2026-10-01). Treat as "MIT-intended, file missing" until confirmed.
- **Activity/versions:** repo created 2026-03-19, last push 2026-03-28 (GitHub API, **V**); requires "Skyrim SE or AE (v1.6.1130+)", SKSE64 + Address Library, Windows only, .NET 10 (**V**, README). 9 stars, 3 forks.
- **Confidence: high.** **What this changes for us:** its `PapyrusBridge`/`TaskQueue`/`EventSystem` source layout is a read-worthy blueprint for our C++ side, and proof a generic VM bridge + named pipe works in 2026; the .NET 10 + Claude Desktop stack is not reusable for a player-facing mod.

### 1.3 Papyrus Stack Stalker

- **What it is:** "Papyrus Stack Stalker is an SKSE plugin that offers an unparalleled, real-time window into the inner workings of Skyrim's Papyrus Virtual [Machine]" ([Nexus 151940, Papyrus Stack Stalker NG](https://www.nexusmods.com/skyrimspecialedition/mods/151940), **U** — snippet only; the page would not open to an automated fetch). Created by **33void**, original upload 2025-06-05, version 1.6, last updated 2025-06-08; ~12k downloads; archived files include an AE build and a Display Tweaks build (**U**, Nexus files/version-history snippets).
- **External-facing or logger?** All available evidence says inspection/monitoring tool only (a "window into" the VM); nothing indicates a call-in API an external process could use. **U, medium confidence.**
- **What this changes for us:** nothing for adoption; useful as a debugging reference for VM stack behaviour. Its source availability is **unknown** (dead end — Nexus 403).

### 1.4 JContainers (Lua), Skyrim Scripting / mrowrpurr, .NET Script Framework

- **JContainers:** original [SilverIce/JContainers](https://github.com/SilverIce/JContainers), SE port [ryobg/JContainers](https://github.com/ryobg/JContainers): "JSON based serializable data structures… Embedded Lua interpreter… C++ API" (**V**); MIT licence (libhunt/trendshift mirror repo metadata: "MIT License", **U**; the SE Nexus page states the port permission rested "on its MIT license", **U**). Latest release **v4.3.0, 2025-08-25**, supporting AE 1.6.1170 / GOG 1.6.1179 / VR 1.4.15 with SKSE 2.2.6 ([github.com/ryobg/JContainers/releases](https://github.com/ryobg/jcontainers/releases), **V**). Separately, a **new "JContainers" Lua runtime** (Nexus 267) advertises "expanded Lua interface and two-way Lua-Papyrus integration", LuaJIT FFI, explicit execution contexts, built with CommonLibSSE-NG, "tested in-game on Skyrim 1.5.97 with SKSE 2.0.20 and Skyrim 1.7.99 with SKSE 2.3.0" (**U**, Nexus snippet, page dated 2026-08-23). A fork "JContainers-NG" (katzmannr) was called out in [issue #38](https://github.com/katzmannr/JContainers-NG/issues/38) for replacing the original MIT notice with GPLv3 (**V**, 2026-08-23) — licence hygiene warning if we ever borrow code.
- **Skyrim Scripting / mrowrpurr:** [github.com/SkyrimScripting](https://github.com/SkyrimScripting) — 32 repositories, "Top languages C++ CMake Lua Papyrus" (**V**). These are SKSE templates/helpers (e.g. `Plugin`, `no-esp` MIT), not a scripting host for players. No embedded-interpreter product found. **Confidence: medium-high.**
- **.NET Script Framework (meh321):** "Framework for memory editing, native code hooking and writing DLL plugins in any .NET language… **Not compatible with Anniversary Edition (patch 1.6.x or later)!!**" ([Nexus 21294](https://www.nexusmods.com/skyrimspecialedition/mods/21294), **U**, snippet). Community consensus: a full rewrite would be required and "won't be happening" ([STEP forum](https://stepmodifications.org/forum/topic/14805-net-script-framework-by-meh321/), **U**). Cautionary tale: deep memory-address frameworks die on game updates.
- **What this changes for us:** JContainers is the proof that an embedded interpreter with two-way Papyrus integration ships to players and survives years of updates; its Lua↔Papyrus event/callback design is the pattern to mirror in Python.

### 1.5 Existing Python bindings / bridges

- **SkyrimPy** ([wabbajack-tools/SkyrimPy](https://github.com/wabbajack-tools/SkyrimPy)): "WIP testing for integrating Python 3 into Skyrim… a SKSE plugin that wraps CommonLibSSE and presents it to Python" (**V**). GitHub API (**V**, 2026-10-01): **MIT licence**, created **and last pushed 2022-02-21**, 3 stars, 9 KB — a one-day skeleton built on halgari's ExamplePlugin-CommonLibSSE template. No released DLL, no dispatcher, no event layer.
- **Heart of Magic** (Nexus): "uses an embedded Python environment to build spell trees… The installer downloads Python 3.12.8 (embedded), pip, and required packages" from an in-game UI, installing `python.exe` under `Data/SKSE/Plugins/SpellLearning/SpellTreeBuilder/python/` ([Nexus articles/11574](https://www.nexusmods.com/skyrimspecialedition/articles/11574), **U**, 2026-02-09). Presence of `python.exe` + `python312._pth` + get-pip strongly implies a **child-process** Python, not in-process embedding (**U/inference**). Also a real MO2 caveat: "MO2's virtual filesystem (USVFS) is hiding the completion marker file… check the MO2 Overwrite folder".
- No pybind11/nanobind Skyrim or Fallout 4 project with any traction found; no JSON-RPC bridge beyond DevBench/SkyLink-style dev tools. **Confidence: medium** (absence-of-evidence).
- **What this changes for us:** the niche is genuinely empty; Heart of Magic shows the embeddable-zip + subprocess route already ships to end users.

### 1.6 Adopt / adapt / build decision

**Build our own plugin; adapt three things:** (1) read SkyLink AI's `PapyrusBridge`/`TaskQueue`/`EventSystem` as a design blueprint (MIT-intended but no LICENSE file — read for ideas, copy nothing verbatim until the licence file lands); (2) reuse the `.psc`→typed-stub toolchain from the Papyrus-2-Typescript lineage (MIT) rather than writing a parser from zero; (3) mirror JContainers' Lua↔Papyrus event/callback architecture. SkyrimPlatform (GPL-3.0) and JContainers-NG (GPLv3 fork) are read-only references for us — GPL contamination would force our whole plugin open under GPL.

**Open unknowns (Q1):**
- Does SkyLink AI's repo actually grant MIT? *Smallest test: open the repo file tree and look for LICENSE; if absent, ask the author.*
- Is Papyrus Stack Stalker NG open source, and does it expose anything beyond logging? *Smallest test: fetch the Nexus page from a browser (blocked to automation) or find 33void's repo.*
- Does SkyrimPlatform run on 1.7.99/1.7.104? *Smallest test: read the latest `docs/release/sp-*.md` in the skymp repo.*

**Dead ends (Q1):** Nexus pages for mods 151940 and 16495 detail tabs refused automated fetch (internal error / 403-class); SkyrimPy has zero working code to evaluate; no FO4/Starfield Python binding surfaced.

# Question 2. Technical feasibility: embedding Python and generating bindings

**Verdict: Feasible, and every hard piece has a proven precedent.** A generic by-name Papyrus dispatcher is a documented CommonLibSSE-NG API (`DispatchStaticCall`/`DispatchMethodCall` with an `IStackCallbackFunctor` result callback — async by design, which maps naturally onto Python futures). Game-thread marshalling is the stock SKSE task interface. `.psc` parsing has three reusable open-source toolchains (Caprica, Champollion, Papyrus-2-Typescript). Embedded-interpreter-in-SKSE is proven by JContainers (Lua) and SkyrimPlatform (ChakraCore); CPython specifically has only a dead one-day experiment (SkyrimPy) and a live child-process precedent (Heart of Magic). The genuinely unproven cells are: CPython embedded in-process inside Skyrim (nobody has shipped it), two CPython runtimes coexisting in the game process (a real hazard if another mod embeds the same `python3xx.dll`), and everything under Proton (no published report either way).

### 2.1 Precedents for an embedded interpreter inside an SKSE plugin

- **JContainers:** embeds Lua (LuaJIT in the new runtime) inside an SKSE plugin, with its own GC and data structures because "there is no source code of the Papyrus virtual machine, it is tricky and no easy to extend the existing Papyrus Array type" ([ryobg/JContainers](https://github.com/ryobg/JContainers), **V**). Shipped for years, actively released (v4.3.0, 2025-08-25, **V**).
- **SkyrimPlatform:** embeds ChakraCore + CEF; init/reload is file-watcher based with hot reload; save/load is its admitted weak point (**V**, README).
- **CPython:** SkyrimPy (in-process wrap of CommonLibSSE, abandoned day one, **V**) and Heart of Magic (embedded-zip Python 3.12.8 run as a child process, **U**).
- **Init timing:** the accepted pattern is *not* DllMain: register SKSE listeners at `SKSEPlugin_Load` and do real work at `kDataLoaded` ("Sent after all of the game plugin files have been loaded") — see the message table at [skyrim.dev/skse/system-messages](https://skyrim.dev/skse/system-messages) (**V**) and the minimal plugin example at [skyrim.dev/skse/first-plugin](https://skyrim.dev/skse/first-plugin) (**V**), plus Papyrus-native registration via `SKSE::GetPapyrusInterface()->Register(...)` whose "registration callback will be called to register your native functions after the VM is initialized" ([cppcooper/MagickaReserve README](https://github.com/cppcooper/MagickaReserve), **V**). Specific loader-lock/crash reports from these projects: none published that I could open. **Confidence: medium-high.**
- **What this changes for us:** start CPython at `kDataLoaded` (or lazily on first script run), never in DllMain; mirror JContainers' "interpreter owns data, Papyrus touches game objects" split.

### 2.2 Two embedded runtimes in one process

- No Skyrim-specific report exists. The general Windows hazard is real: if two mods each embed CPython of the **same** version, both need `python312.dll`, and Windows module resolution plus CPython's process-global state (pre-free-threading GIL, global config) make a second independent in-process interpreter of the same DLL fragile; mismatched-version coexistence produces the classic `ImportError: Module use of python312.dll conflicts with this version of Python` seen in the wild ([Nordic DevZone thread](https://devzone.nordicsemi.com/f/nordic-q-a/118494), **U**, 2025-01-30; [stable-diffusion-webui #14502](https://github.com/AUTOMATIC1111/stable-diffusion-webui/discussions/14502), **U**). These are environment-mixing cases, not game mods — **label U, extrapolation flagged**.
- Safe options in increasing order of safety: isolated `PyConfig` + private DLL directory (same process, still risky against a same-version twin); renamed/re-versioned private build (works but breaks binary wheel compatibility that expects `python3xx.dll` by name); **separate child process** (the KiCad/Heart-of-Magic pattern — immune by construction).
- **Confidence: medium** (no Skyrim case law). **What this changes for us:** this is the strongest technical argument for hosting option (B), the hidden child process — process isolation makes the two-runtime problem disappear entirely.

### 2.3 In-process vs out-of-process hosting in game mods

- In-process shipped at scale: JContainers (Lua), SkyrimPlatform (ChakraCore). Out-of-process shipped at scale: **KiCad 9's IPC API** — "Python plugins are run by an external Python interpreter (unlike the SWIG-based plugins which run in an interpreter embedded into KiCad)", connecting over "a Unix domain socket on macOS and Linux, and a named pipe on Windows", with a per-instance `KICAD_API_TOKEN` ([KiCad dev docs](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/for-addon-developers/index.html), **V**, opened 2026-10-01); the SWIG in-process bindings are in "maintenance mode" ([atopile/kicad-python](https://github.com/atopile/kicad-python), **V**). Heart of Magic (out-of-process Python for a Skyrim mod, **U**).
- Crash isolation: out-of-process wins trivially — a scripting crash kills the child, not the game. Hot reload: SkyrimPlatform shows in-process reload works (file watcher, **V**); JContainers users report quick-save/reload workflows with Lua ([geek-of-all-trades tutorial](https://geek-of-all-trades.neocities.org/programming/skyrim/lua-jcontainers), **U**). Unload: SKSE plugins are never truly unloaded at runtime, so "unload" means teardown of interpreter state at save-load boundaries — no published pattern found. **Confidence: medium-high.**
- **What this changes for us:** KiCad 9 is the direct modern precedent for our option (B), including token auth and per-plugin venvs; their forum also documents early-adopter UX pain (manual runtime selection, silent plugin-load failures) worth designing against ([forum thread](https://forum.kicad.info/t/kicad-9-0-python-api-ipc-api/57236), **U**).

### 2.4 `.psc` parsing and stub generation

- **Caprica** ([Orvid/Caprica](https://github.com/Orvid/Caprica)): "An MIT licensed compiler for the Papyrus scripting language" (**V**); compiles Skyrim/FO4/FO76 scripts; C++, MSVC/PPL-bound. Latest release page exists (2023-10-02, **U**).
- **Champollion** ([Orvid/Champollion](https://github.com/Orvid/Champollion)): PEX→psc decompiler for "Skyrim, Fallout 4, Fallout 76, and Starfield", **LGPL v3** (**V**). Fine as a dev-time tool; don't link it.
- **pyro** ([fireundubh/pyro](https://github.com/fireundubh/pyro)): Python build automation wrapping PapyrusCompiler/Caprica, "Parallelized, Incremental Build Automation for TESV, SSE, and FO4" (**V**); open PRs from 2023–2024 sit unanswered — **maintenance is stale**.
- **Papyrus-2-Typescript** (MIT, last push 2023-02-06, **V** via GitHub API): converts `.psc` headers to `.ts` — the closest existing artefact to the stub generator we need; its Nim parser handles "function headers" only, verbatim-dumps bodies.
- Other parsers: fireundubh's **OpenPapyrus ANTLR4 grammars for Papyrus** ([github.com/fireundubh](https://github.com/fireundubh), **V**, pinned repo) — an ANTLR grammar is arguably the best foundation for a Python stub generator.
- **Header distribution:** SKSE ships its `.psc` sources inside the SKSE archive; PO3 Papyrus Extender is MIT with sources in its repo (settled in Part A). Vanilla headers come with the CK/base game scripts. No licence blocker for *reading* headers at dev time; redistributing generated stubs derived from Bethesda/SKSE headers in the mod is standard practice (SkyrimPlatform ships `skyrimPlatform.ts` similarly) but is **R-level** — no authoritative statement found.
- **Confidence: high.** **What this changes for us:** write our own small `.psc`-header parser in Python (grammar exists to crib from OpenPapyrus; semantics cribbed from Papyrus-2-Typescript); do not embed Caprica/Champollion in the pipeline at runtime.

### 2.5 Calling Papyrus from C++ by name

- The documented pattern is `RE::BSScript::IVirtualMachine::DispatchStaticCall(const BSFixedString& a_className, const BSFixedString& a_fnName, IFunctionArguments* a_args, BSTSmartPointer<IStackCallbackFunctor>& a_result)` and `DispatchMethodCall` overloads by bound object or VM handle ([ng.commonlib.dev IVirtualMachine reference](https://ng.commonlib.dev/classRE_1_1BSScript_1_1IVirtualMachine.html), **V**, opened 2026-10-01). Results arrive through the `IStackCallbackFunctor` — inherently async, which is exactly what a Python `Future` wants. Latent calls are first-class: `IsWaitingOnLatent`/`ReturnFromLatent` are on the same interface (**V**).
- Known pitfalls: no opened source documents crash rates for by-name dispatch; SkyLink AI ships a "VM call bridge" over exactly this kind of interface with a catalog of 3,389 functions from 166 scripts (**V**) — existence proof that generic dispatch plus argument marshalling is workable today. VM overload/stack-dump hazards are Papyrus folklore (R); treat latency as unmeasured until the Part C live tests.
- **Confidence: high** for the API surface; **low** for performance characteristics. **What this changes for us:** no reverse engineering needed for the dispatcher — CommonLibSSE-NG already exposes it; our Python async API maps 1:1 onto the callback functor.

### 2.6 Game-thread safety

- Accepted pattern: `SKSE::GetTaskInterface()->AddTask(...)` — tasks run on the game's task thread; example from Ryan-rsm-McKenzie's CommonLibSSE task-interface gist: "auto task = SKSE::GetTaskInterface(); … task->AddTask([](…){…});" ([gist](https://gist.github.com/Ryan-rsm-McKenzie/90e9e3bde1584fcdac0c9feb1e352586), **V**). Practical hazard documented by practitioner experience: "The SKSE task queue drains pop-until-empty each pass, so a task that re-queues itself runs again in the *same* drain — the whole 'loop' executes inside one frame and hard-freezes the main thread (field-verified, twice)" ([SKSE Plugin Authoring notes](https://www.skillsdirectory.com/skills/shugokifable-skse-plugin-authoring-050a6d13), **U**, 2026-09-03).
- Reference representation: comparable projects pass `FormID`/handles — e.g. `TESHitEvent` carries `NiPointer<TESObjectREFR>` for actors but plain `FormID` for weapon/projectile ([TESHitEvent struct ref](https://ng.commonlib.dev/structRE_1_1TESHitEvent.html), **V**) — and the VM itself uses `VMHandle` for bound objects (**V**, IVirtualMachine). Our "form handle, not raw pointer" rule matches the engine's own idiom. Dangling-reference-after-cell-change guidance in published docs: not found as a single authoritative statement (**gap**).
- **Confidence: high** on the pattern, **medium** on hazard coverage. **What this changes for us:** Python worker thread → `AddTask` one-shot closures → callback functor → resolve future; never re-queue from inside a task.

### 2.7 Event sinks in CommonLibSSE-NG

- The event structs exist as documented RE classes (e.g. `TESHitEvent` with target/cause/source/projectile/flags incl. `kPowerAttack`, `kSneakAttack`, `kHitBlocked`, **V**). The full menu of TES event sinks (equip, container changed, cell attach/detach, menu open/close, quest stage, save/load via SKSE `kSaveGame`/`kPreLoadGame`/`kPostLoadGame` messages — message table **V** at skyrim.dev) is standard CommonLibSSE-NG fare; SkyLink AI's "17 event types: combat, death, quests, location, inventory, equip, hits, spells, activate" (`EventSystem.*`, **V**) shows a working sink set in a 2026 codebase. Per-event caveats (e.g. death event firing order vs. `OnDeath` Papyrus scripts, cell-attach spam rates): no opened source enumerates them — **gap, marked low confidence**.
- **What this changes for us:** event coverage is a solved problem at the C++ level; the design work is all on the Python side (subscription lifetime, save/load resubscription).

- Two-runtime collision: is any shipped mod already embedding `python3xx.dll` in-process? *Smallest test: scan the top 200 SKSE mods' DLL directories for `python*.dll` (Heart of Magic's is a child process, so likely none).*
- Save/load with a live interpreter: state teardown ordering vs. SKSE cosave. *Smallest test: Part C live test 3.*

- Event-sink per-event caveats: *Smallest test: subscribe to death + hit in-game and diff against Papyrus `OnDeath`/`OnHit` logs (Part C test 6).*
